# FamilyCare v0.4.0 Release

## Overview

FamilyCare Web, API, and Analyzer Worker now share the `0.4.0` product identity. This minor release
packages the insurance-ledger reconciliation boundary, consolidated coverage-ledger UI, stale
unreadable-source correction, release-publication fixes, documentation refresh, and development-tool
maintenance completed after `v0.3.2`.

The release remains a container publication, not an operational deployment. The tag workflow owns
the immutable GitHub commit, three GHCR image digests, and generated GitHub Release evidence. The
protected WSL runtime remains on its previously recorded `v0.3.2`/migration `0023` baseline unless a
separate migration and redeployment is explicitly approved.

## Context

- Commits after `v0.3.2` include PR #49 through PR #57.
- PR #50 and PR #51 replaced two stale Dependabot pull requests on current `main`, synchronized both
  lockfiles, passed all required CI, and left no open Dependabot PR or alert.
- PR #54 corrected current unreadable-work projection without deleting failure history.
- PR #55 and PR #56 added append-only reconciliation history, exact member-scoped APIs, and one
  coverage-ledger summary. PR #57 recorded count-only protected acceptance.
- PR #49 and PR #53 repaired CHANGELOG-derived Release notes and the `runner.temp` workflow parser
  boundary. `v0.4.0` is the first deliberate tag that exercises both fixes together.
- `0.4.0` is a backward-compatible minor increment because it adds public reconciliation API
  operations and response schemas rather than only correcting existing behavior.

## Changes Made

### Product release identity

- Updated API, Worker, and Web package metadata to `0.4.0`.
- Updated the API and Worker runtime package constants and synthetic health-response assertions.
- Regenerated only the two editable FamilyCare package versions in `uv.lock`.
- Regenerated the canonical OpenAPI snapshot; its only release-identity changes are
  `info.version` and the health response's default version.

### Release and project documentation

- Promoted the accumulated `[Unreleased]` entries into the dated `0.4.0` CHANGELOG section and added
  the reconciliation API/UI, stale-failure, exact-link, and concurrency boundaries.
- Updated README, architecture, guide, roadmap, foundation, test, security, product-design, and
  contract inventory status to the `v0.4.0` baseline.
- Preserved historical plans and specifications that correctly describe `v0.3.2` or earlier work;
  their version references were not mechanically rewritten.

### Release execution contract

- The release branch must pass the full local gate and all seven required PR checks before merge.
- The merged `main` commit must pass post-merge CI before an annotated `v0.4.0` tag is pushed.
- The tag workflow must rebuild and publish Web, API, and Worker serially, prove each version tag and
  `sha-<commit>` tag resolve to the same digest, and reject a shared digest across components.
- The GitHub Release must contain real Markdown under `Changes`, `Release evidence`, and
  `Privacy and deployment boundary`.
- Exact workflow run, commit, and digest evidence is generated only after the immutable tag exists;
  it belongs in the GitHub Release rather than being predicted in this pre-tag repository record.

## Privacy and Security Boundary

- No actual insurance or medical document, extracted content, OCR output, personal identifier,
  private path, credential, database value, or protected row-level result was opened or committed.
- Tests and committed contracts use synthetic data created for the repository.
- The prior protected acceptance is referenced only through already recorded aggregate counts and
  boundaries; this release preparation performs no protected database read or write.
- The tag workflow uses repository code, synthetic CI inputs, and GitHub-provided publication
  credentials. It does not use external AI, Google Drive, actual PDFs, or runtime secrets.

## Remaining Boundaries

- Publishing GHCR images and a GitHub Release does not migrate or deploy the protected runtime.
- Migration `0024`, service recreation, exact contract linking, and unresolved-source disposition
  require a separately approved operational pass.
- Windows browser, physical mobile PWA, remaining actual document/OCR variants, actual provider
  behavior, Cloud Run, and full disaster recovery remain unverified.
- Completed release branches and any dedicated worktrees are removed only after merge and tag
  verification; the immutable release tag remains by design.
