# FamilyCare v0.1 product design

- 상태: Phase 2~8 구현·local acceptance 및 `v0.1.0` 공개 완료; 후속 private knowledge와
  `v0.2.0`~`v0.3.2`는 roadmap과 별도 설계가 소유
- 작성일: 2026-08-24
- 적용 범위: Phase 2부터 Phase 8, `v0.1.0` 로컬 사용 승인
- 선행 조건: Phase 1 Synthetic PDF Ingestion 완료

## Scope

FamilyCare v0.1은 가족의 보험증권과 약관을 로컬 WSL 환경에서 분석해 실제 가입 담보 원장을 만들고, 병원 방문 전후의 상황에 맞는 청구 검토 대상을 근거와 함께 제시하며, 실제 청구 결과까지 기록하는 첫 사용 가능 버전이다.

이 버전의 성공 기준은 기능 목록의 존재가 아니다. 사용자가 다음 흐름을 끊김 없이 완료할 수 있어야 한다.

```text
로그인
  -> 가족 선택
  -> 증권·약관 일괄 가져오기
  -> AI 구조화와 근거 검증
  -> 가입 담보 원장 확인
  -> 병원 방문 전 또는 치료 후 사건 입력
  -> MATCH / NO_MATCH / UNKNOWN 판정과 예상액 확인
  -> 근거 페이지 확인
  -> 보험사별 청구 준비·접수·지급 이력 기록
```

## Goals

1. 증권에서 확인된 실제 가입 담보와 약관 조건을 연결한다.
2. 사용자가 모든 추출 후보를 먼저 검수하지 않아도 AI 검증 결과를 즉시 활용한다.
3. 불완전한 사전 입력과 상세한 사후 입력을 같은 사건 수명주기로 지원한다.
4. 정액형과 실손형을 분리해 계산하고, 불완전한 계산도 확인된 부분을 보존한다.
5. 모든 결과에서 증권·약관 페이지와 적용 규칙을 다시 확인할 수 있게 한다.
6. 분석 후보와 실제 청구·지급 결과를 서로 다른 기록으로 관리한다.
7. 개인 WSL의 Docker Compose에서 실행하고 Tailscale을 통해 부부의 허용 기기에서 사용한다.

## Non-goals

- 보험금 지급 보장 또는 보험사의 최종 심사 대체
- 보험사 API를 통한 직접 청구 제출
- 진단서·영수증·처방전 같은 의료 문서 파일 보관
- Google Drive 자동 동기화
- Cloud Run 또는 공용 인터넷 운영 배포
- 다중 가정, 공개 회원가입, 초대, 역할별 권한, 결제
- LUKS, BitLocker, WSL swap 변경, 별도 고정 크기 암호화 볼륨
- 임의 Python·SQL·JavaScript를 실행하는 보험 규칙

## Users and ownership

- `AppUser`는 로그인하는 관리자이며 v0.1에는 동일 권한 로컬 관리자 계정 두 개만 존재한다.
- 두 계정은 하나의 `HouseholdSpace`를 공유한다.
- `FamilyMember`는 보험 대상이며 `AppUser`와 별도 수명주기를 가진다.
- 모든 Phase 2 이후 업무 데이터는 서버가 현재 세션에서 계산한 `HouseholdSpace` 범위를 가진다.
- 클라이언트가 보낸 사용자·가정 식별자를 권위 있는 접근 범위로 사용하지 않는다.

## Primary user flows

### 1. Family and document intake

사용자는 먼저 보험 대상 가족 구성원을 선택하거나 만든다. 한 번의 가져오기 배치에는 한 가족 구성원의 문서만 넣는다. 문서 소유자를 PDF 암호로 추측하지 않는다.

배치는 여러 증권, 약관, 상품설명서, 청약서와 보조자료 PDF를 받는다. 암호화된 문서는 해당 배치에서 암호를 한 번 입력하고 메모리에서만 재사용한다. 일부 파일의 암호가 다르거나 잘못됐으면 성공 파일은 계속 처리하고 실패 파일만 다시 묻는다. 상품설명서와 청약서는 약관이나 확정 계약 근거로 사용하지 않는다.

한 PDF가 여러 보험이나 여러 문서 역할을 포함할 수 있으므로 source 파일을 검수된 page-range component로 나눈다. filename과 intake kind는 힌트일 뿐이며 등록 보험과 문서 보유 현황은 component와 보험별 document set을 기준으로 계산한다.

처리 단계는 다음 사용자 상태로 투영한다.

```text
대기 -> 추출 -> 선택적 OCR -> AI 구조화 -> AI 검증 -> 완료
                                           -> 부분 완료
                                           -> 사용자 확인 필요
                                           -> 실패
```

원장 aggregate와 candidate review 계약은 `docs/design/policy-ledger.md`를 따른다.

분석 완료 뒤에는 가족별로 증권+약관, 증권만, 미연결 약관, 상품설명서, 판독 필요 자료를 구분해 보여 준다. 증권 근거가 없는 자료는 `가입 확인 안 됨` 영역에 유지하며 세부 계약은 `docs/design/insurance-document-inventory.md`를 따른다.

### 2. AI-assisted policy ledger

AI는 증권의 계약, 당사자 역할, 보험기간, 실제 가입 담보, 가입금액, 갱신 여부와 페이지 근거를 후보로 만든다. 별도의 AI 호출이 각 후보와 원문 근거의 일치를 검증하고, 프로그램 검증기가 스키마·단위·페이지·Evidence 불변조건을 확인한다.

후보 상태는 다음 세 개다.

- `AI_VERIFIED`: 두 AI 단계와 프로그램 검증을 통과해 즉시 사용할 수 있다.
- `NEEDS_REVIEW`: 근거 부족, 상충, 낮은 신뢰 또는 지원하지 않는 구조가 있다.
- `USER_CONFIRMED`: 사용자가 원문을 확인해 승인하거나 수정했다.

사용자 수정은 원시 추출과 AI 결과를 덮어쓰지 않는다. 수정값, 수정자, 시각, 이전 값과 Evidence를 새 버전으로 기록한다. 약관에만 있는 담보는 어떤 AI 상태에서도 가입 Rider가 될 수 없다.

### 3. Terms, clauses, and executable rules

약관은 판본별 `TermsEdition`으로 관리하고 장·절·조·항·별표를 `Clause`로 구조화한다. 실제 가입 Rider와 관련 Clause의 연결도 AI 후보, AI 검증, 프로그램 검증을 거친다.

AI는 다음 규칙 후보를 구조화할 수 있다.

- 피보험자·계약·담보 자격
- 질병·상해·진단·수술·입원·통원 분류
- 보장개시, 대기기간, 감액기간
- 면책과 제외
- 최초 1회, 일·회·연간 횟수 제한
- 정액 지급액, 가입금액 비율, 일수 계산
- 실손 대상 범주, 공제, 보상 비율, 한도
- 필요서류와 추가 확인 사실

검증된 Evidence와 허용 DSL로 표현할 수 없는 복잡한 문장은 정보용 후보로 남기고 실행하지 않는다. 그 규칙에 의존하는 판정은 `UNKNOWN`이다.

조항 구조·검색·Rider link 계약은 `docs/design/clause-linking-search.md`를 따른다.

### 4. Pre-visit and post-treatment input

입력은 자연어와 구조화 필드를 결합한 하이브리드 방식이다.

1. 사용자가 현재 상황을 자연어로 입력한다.
2. AI가 가족, 사건일, 질병·상해, 증상·진단, 치료, 입원·통원 등을 구조화한다.
3. 화면은 추출 결과를 수정 가능한 항목으로 표시한다.
4. 사용자가 별도 확정 단계를 거치지 않아도 명확한 값으로 현재 후보를 바로 분석한다.
5. 애매하거나 빠진 필드는 `UNKNOWN`으로 보존하고 선택형 추가 질문을 제공한다.

병원 방문 전에는 증상과 예정 진료만으로 넓은 후보와 준비사항을 보여준다. 치료 후에는 같은 `MedicalEvent`를 진단, 수술, 입퇴원, 통원, 비용 자료로 보강한다.

Web 입력과 행동 우선 result 계약은 `docs/design/event-result-pwa.md`를 따른다.

### 5. Deterministic decision engine

AI는 입력과 약관을 구조화하지만 `MATCH`, `NO_MATCH`, `UNKNOWN`이나 보험금 예상액을 직접 결정하지 않는다. API의 결정론적 엔진이 버전 있는 사실과 규칙을 평가한다.

평가 순서는 다음과 같다.

1. FamilyMember와 PolicyParty 관계
2. 사건일과 보험기간
3. 실제 가입 Rider와 사고일 상태
4. 질병·상해 등 상위 분류
5. 보장개시·대기·감액기간
6. 지급사유 정의와 별표 분류
7. 면책·횟수·과거 지급 이력
8. 정액 또는 실손 계산

정보 부족은 오류나 불일치가 아니다. 결정적인 반대 근거가 있을 때만 `NO_MATCH`이며, 그 밖의 부족·상충·갱신 미확인은 `UNKNOWN`이다.

### 6. Fixed-benefit and indemnity calculation

정액형은 가입금액, 고정 금액 또는 비율, 감액, 횟수·일수, 통화, 반올림 규칙과 중간 계산값을 보존한다.

실손형은 사용자가 입력한 통원·입원·약제비 영수증 항목을 급여 본인부담금, 비급여, 제외 가능 항목, 실제 지출액으로 구조화한다. 확인된 규칙만 계산에 사용하고 다음 값을 나눠 보여준다.

- 현재 확인된 청구 검토 금액
- 추가 확인이 필요한 금액
- 제외된 금액과 이유
- 적용한 공제·비율·한도
- 영수증 항목과 약관 Evidence

복수 실손 특약은 보험사별 독립 예상액을 합산하지 않는다. 공통 청구 검토 항목과 각 계약 조건을 보여주고, 최종 비례분담은 확인 전까지 `UNKNOWN`으로 둔다.

### 7. Action-first result experience

모바일 결과 화면은 승인된 행동 우선 카드 구조를 사용한다.

1. 지금 할 일
2. 청구 검토 대상
3. 추가 확인 필요
4. 결정적 불일치
5. 조건부 예상액과 보류 이유
6. 증권·약관 원문 근거

근거는 처음부터 긴 보고서로 펼치지 않고 카드에서 필요할 때 연다. 결과 표현은 지급 확정이 아니라 청구 검토, 확인 필요, 불일치로 제한한다.

### 8. Claim workflow

하나의 `MedicalEvent` 아래 보험사·계약별 `ClaimCase`를 만든다. ClaimCase는 당시의 후보, 규칙, 예상액, Evidence를 스냅샷으로 보존한다.

상태는 다음을 사용한다.

```text
preparing
  -> submitted
  -> supplementation_requested
  -> paid | partially_paid | denied
  -> closed
```

각 청구에는 필요서류 체크리스트, 예상 청구 항목, 접수번호·접수일, 실제 청구액·지급액·지급일, 감액·거절 사유와 변경 이력을 기록한다. v0.1은 의료 문서 파일을 저장하거나 보험사에 직접 제출하지 않는다.

상태 전이와 snapshot 계약은 `docs/design/claim-workflow.md`를 따른다.

## Architecture

```text
Web PWA
  -> FastAPI modular monolith
       -> PostgreSQL business data, audit, and job queue
       -> Analyzer Worker
            -> PDF extraction and selective local OCR
            -> OpenAI structuring call
            -> independent OpenAI verification call
            -> deterministic schema and evidence validation
  -> local encrypted managed document archive
```

### Web PWA

Web은 입력, 수정, 작업 상태, 결과 카드, Evidence 탐색, 청구 이력을 담당한다. 보험 규칙과 금액 계산은 소유하지 않는다. 서비스 워커는 앱 셸만 캐시한다.

### FastAPI modular monolith

- `identity`: 두 관리자, 공동 HouseholdSpace, 세션
- `documents`: 가져오기 배치, 문서, 추출, Evidence, 관리 archive 참조
- `policies`: 계약, 당사자, 실제 가입 Rider, 상태 스냅샷
- `clauses`: 약관 판본, 조항, Rider 연결, 전문검색
- `decisions`: 의료사건, 규칙, 평가, 계산, 결과 스냅샷
- `claims`: 체크리스트, 접수, 지급, 상태·감사 이력

모듈은 다른 모듈의 내부 테이블을 직접 변경하지 않고 공개 유스케이스와 읽기 모델을 사용한다.

### Analyzer Worker

Worker만 PDF 파싱, OCR, 외부 AI 호출을 수행한다. `OPENAI_API_KEY`는 Worker 컨테이너에만 주입한다. AI 제공자·모델은 구성 가능한 adapter이며 도메인 모델이나 판정 엔진 계약이 특정 모델명을 소유하지 않는다.

### PostgreSQL and contracts

PostgreSQL은 업무 데이터, 전문검색, 감사 이력, 작업 큐를 함께 담당한다. Redis, 별도 검색 서버, 벡터 데이터베이스를 v0.1에 추가하지 않는다. `packages/contracts`의 OpenAPI와 JSON Schema가 Web/API/Worker 경계의 기준이다.

## AI authority and data boundary

- OpenAI에는 전체 PDF binary, PDF 암호, 실제 로컬 경로, 인증정보를 보내지 않는다.
- Worker는 필요한 페이지의 추출 텍스트와 좌표·내부 Evidence ID만 제한된 크기의 batch로 전송한다.
- 이름·연락처·증권번호처럼 판정에 불필요한 직접 식별자는 전송 전에 제거한다.
- 담보명, 가입금액, 기간과 약관 문장은 구조화에 필요한 경우 전송할 수 있다.
- 1차 구조화와 2차 검증은 분리된 요청이며 검증기는 새 사실을 발명할 수 없다.
- AI 응답은 strict schema, Evidence 존재, 단위, 허용 연산자, 상충 검사에 실패하면 실행되지 않는다.
- OpenAI 장애 후에도 기존 원장, 규칙, 판정, Evidence 조회와 수동 보정은 사용할 수 있다.
- v0.1은 `GEMINI_API_KEY`를 사용하지 않는다.

세부 계약은 `docs/design/ai-document-analysis.md`를 따른다.

## Authentication and session

- 로컬 관리자 계정은 정확히 두 개까지 생성하며 동일 권한이다.
- 비밀번호는 Argon2id hash로 PostgreSQL에 저장하고 평문을 환경변수나 저장소에 두지 않는다.
- 세션은 PostgreSQL에 저장하고 브라우저에는 `Secure`, `HttpOnly`, `SameSite=Strict` cookie만 둔다.
- 비활성 7일 또는 절대 30일에 만료하며, 비밀번호·세션 관리 같은 민감 작업은 재인증한다.
- 공개 회원가입, 이메일 reset, 초대, 역할 관리 기능은 없다.

세부 계약은 `docs/design/authentication.md`를 따른다.

## Local runtime

- 개인 PC의 WSL에서 Docker Compose로 Web/API/Worker/PostgreSQL을 실행한다.
- 외부에 공개하는 진입점은 Web gateway 하나이며 API·Worker·PostgreSQL은 Compose 내부 네트워크에 둔다.
- 부부 기기는 Tailscale private network를 통해 Web gateway에 접근한다.
- Cloud Run, 공개 DNS, 공용 인터넷 ingress는 v0.1 범위가 아니다.
- LUKS, BitLocker, WSL swap과 다른 프로젝트의 시스템 설정은 변경하지 않는다.
- 원본 PDF는 Google Drive에 계속 보관하지만 v0.1은 Drive API를 사용하지 않는다.
- Google Drive에서 수동으로 받은 PDF를 가족별 batch로 가져온다.

세부 계약은 `docs/design/private-data-runtime.md`를 따른다.

## Failure and recovery

- batch의 각 문서는 독립적으로 처리하며 한 문서 실패가 성공 문서를 되돌리지 않는다.
- 일시적 DB·네트워크·OpenAI 오류만 제한적으로 자동 재시도한다.
- password 오류는 자동 반복하지 않고 해당 파일만 다시 입력받는다.
- 재분석은 새 버전을 만들며 검증 통과 전 기존 현재 버전을 바꾸지 않는다.
- 일부 규칙·영수증 항목만 해석할 수 없어도 확인된 결과는 보존한다.
- 판정·계산 예외를 0원 또는 `NO_MATCH`로 변환하지 않는다.
- 실패 상태는 안정적인 오류 코드, 실패 단계, 사용자가 취할 다음 행동을 제공한다.

## Test strategy

v0.1의 테스트는 다음을 모두 포함한다.

- 규칙 연산자와 정액·실손 계산의 결정표 단위 테스트
- 암호·표·OCR 필요·손상 형태의 완전 합성 PDF fixture
- 합성된 AI 응답을 사용하는 구조화·검증·재시도 계약 테스트
- 실제 PostgreSQL에서 API, Worker, 원장, 규칙, 사건, 판정, 청구를 잇는 통합 테스트
- 하이브리드 입력과 행동 우선 결과 화면의 Web 컴포넌트 테스트
- 로그인부터 청구 기록까지 핵심 브라우저 E2E
- Web/API/Worker 개별 이미지 build와 Compose 재시작·데이터 보존 스모크 테스트
- 저장소, 로그, 브라우저 cache, 임시 파일의 민감정보 경계 테스트

공개 CI는 실제 자료, OpenAI, Google Drive, 실제 비밀값 없이 실행한다. 실제 PDF와 모바일 기기 acceptance는 로컬 자동검증과 분리해 사실대로 기록한다.

## Delivery slices

각 변경은 독립 검토 가능한 PR로 나눈다.

1. v0.1 설계·로드맵·계획
2. 가족·계약·Rider 원장
3. AI 추출 후보 검증과 원장 UI
4. 약관 구조화와 전문검색
5. Rider-Clause 연결과 실행 규칙 검증
6. MedicalEvent와 tri-state 엔진
7. 정액·실손 계산
8. 하이브리드 입력과 행동 우선 결과 PWA
9. 청구 체크리스트와 지급 이력
10. 두 관리자 인증과 세션
11. 암호 PDF batch와 관리 archive
12. 선택적 로컬 OCR과 검토
13. WSL Compose·Tailscale·비공개 자료 acceptance
14. `v0.1.0` 릴리스 준비와 GHCR 게시

구현 순서와 파일·테스트·커밋 단위는 이 문서 승인 후 `docs/plan/`에서 작성한다. 기능 PR은 합치지 않으며, 각 PR 직전에 root agent가 전체 diff와 최신 검증을 한 번 집중 검토한다.

## Acceptance criteria

1. 두 관리자 중 하나가 로그인해 가족별 문서를 batch로 가져올 수 있다.
2. 암호 문서는 batch 동안 한 번 입력한 암호로 처리되며 DB·job·log에 암호가 없다.
3. AI 검증된 계약·Rider·Clause·CoverageRule은 원문 Evidence와 함께 즉시 사용할 수 있다.
4. 미확인·상충 후보는 자동 확정되지 않고 종속 판정이 `UNKNOWN`이다.
5. 병원 방문 전 자연어 입력만으로 현재 청구 후보와 선택 질문을 볼 수 있다.
6. 치료 후 영수증 항목을 입력해 정액과 실손의 조건부 예상 결과를 볼 수 있다.
7. 복수 실손 예상액은 합산되지 않고 비례분담 미확인이 표시된다.
8. 결과 카드에서 다음 행동, 미확인 조건, 증권·약관 페이지 근거를 확인할 수 있다.
9. 보험사별 청구 준비·접수·지급 결과와 이력이 보존된다.
10. Docker Compose 재시작 뒤에도 관리 데이터와 encrypted archive를 읽을 수 있다.
11. 실제 문서·파생물·암호·키·의료 입력이 Git, 일반 로그, 서비스 워커 cache에 없다.
12. PR/main CI와 로컬 회귀검사가 외부 비밀값 없이 통과한다.
13. 사용자가 지정한 저장소 밖 표본으로 실사용 검수를 수행하고 미지원 형식을 기록한다.
14. 모든 기능 PR merge와 post-merge 검증 후 `v0.1.0` 태그의 Web/API/Worker GHCR 게시가 성공한다.

## Deferred after v0.1

- Google Drive 읽기 전용 자동 동기화
- Gemini 또는 다중 AI 제공자 failover
- 보험사 직접 청구 API
- 의료 문서 관리
- 복수 실손 비례분담 자동 계산의 확대
- Cloud Run 또는 다른 운영 배포
- 다중 가정과 계정 초대
- 호스트 전체 디스크·swap 암호화 변경
