# 합성 데이터의 조회·문서 처리·검수 동시 실행 측정

2026-09-09 UTC, source `5e8d9b777e025efb2705d377a250bb12b1ded53d`, schema
`0070_semantic_activity`에서 고정 20개 사례를 새 합성 PostgreSQL 데이터베이스에
준비하고 서비스 조회 200건을 측정했다. 후보 결과는 모두 기존 주요/조건부 후보 기대값과
일치했다. 금액 정확도나 전체 보호 자료의 성능을 검증한 결과는 아니다.

## 환경과 측정 경계

WSL의 PostgreSQL 컨테이너는 2 CPU/1 GiB 제한을 사용했다. 조회 시간은
`DecisionService.analyze_medical_event` 호출부터 PostgreSQL 저장·결과 반환까지이며,
HTTP·인증·브라우저 표시 시간은 제외한다. 사례 준비 뒤 첫 측정과 반복 측정을 구분했지만
DB/OS cache를 비우지 않았으므로 cold-start 성능이라고 부르지 않는다.

검수 부하는 실제 SDK의 MockTransport, 검수 Worker, source 검증과 API projector를
거치는 20개 job이었다. 응답은 합성 원문의 참조 제안에서 만들었고 외부 HTTP 전송을
차단했다. 실제 모델·네트워크 지연이나 비용은 포함하지 않는다. 별도의
[실제 20건 선택 검수 평가](v0.5-fixed-review-evaluation.md)와 합산하지 않는다.

문서 부하는 합성 PDF 10개/250쪽을 기존 분석 API로 접수해 native 추출 Worker와
상태 조회까지 실행했다. 새 암호화 batch/archive 경로나 OCR은 이 부하에 포함하지 않았다.
모든 문서는 처음부터 합성했으며 보호 DB와 기존 유료 평가 DB를 재사용하지 않았다.

## 결과

백분위는 정렬한 측정값의 nearest-rank 방식이다.

| 구간 | 조회 수 | p50 | p95 | 최댓값 | 배경 작업 진행 중 시작한 조회 |
|---|---:|---:|---:|---:|---:|
| 사례별 첫 측정 | 20 | 0.715s | 0.985s | 0.985s | 해당 없음 |
| 반복 조회 | 60 | 0.701s | 0.946s | 1.019s | 해당 없음 |
| 검수와 병행 | 60 | 0.788s | 1.043s | 2.855s | 60/60 |
| PDF 처리와 병행한 측정 실행 | 60 | 0.726s | 1.017s | 1.156s | 24/60 |

PDF 구간은 처리 종료 후 조회 36건도 포함한 전체 실행의 분포다. 실제 경합 중인
24건만의 p95로 해석하지 않는다. 배경 작업 진행 여부는 각 조회 시작 시점에 확인했다.

검수 20건과 문서 10건은 모두 완료됐고 추출 페이지 수는 각 25쪽이었다. 문서 작업의
임시 디렉터리가 비었으며 외부 요청은 0이었다. 200회 조회의 후보 기대값 일치를
확인했지만 기존 companion의 고정 금액 3건 미산정은 해소됐다고 주장하지 않는다.

실행 명령은 소스 worktree에서
`TMPDIR=/tmp PYTHONPATH=. uv run python /tmp/familycare-v053-ops/synthetic_load_acceptance.py`였으며
exit 0이었다. helper·JSON 결과·로그는 저장소 밖 합성 실행 기록으로 보존했다. 전체 보호 자료 크기에서의
DB intake/archive/실제 AI 경합, 실제 기기 응답성과 PWA 설치는 별도 미검증이다.
