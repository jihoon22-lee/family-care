# v0.5.0 release preparation

통합된 로컬 청구 안내·보관 원문 재처리의 제품 버전을 0.5.0으로 맞추고, 실제 실행한 수용과
미지원 범위를 현재 문서에 연결했다. API/Worker pyproject와 runtime 버전, Web package,
uv.lock, OpenAPI health/default, health 테스트와 CHANGELOG를 함께 변경했다. 생성 Web
계약은 재생성했으며 타입 내용의 추가 변경은 없었다.

README·보안/구조 문서·로드맵과 B07/B08·수용 원장은 현재 코드와 과거 실행을 구분한다.
전체 자료의 자동 해석은 PARTIAL이며 자동 약관 판본/의미 지식, 읽지 못한 자료와 정확한
과거 별칭 연결을 성공으로 집계하지 않는다. 실제 값·개수·경로·식별자는 공개하지 않는다.

## Protected acceptance boundary

제품 입력이 동일한 `a6445be`/0069에서 기존 행·원문 식별/hash 보존, 원본 응답의 로컬
축소·실제 독립 검수 1회·프로그램 검사·선택 후보 원장 반영을 확인했다. 새 clone의
AI-off 인증·기존 결과/청구·원문과 Windows Chrome 사용 흐름도 통과했다. `49e5679`에서
첫 API 프로세스 조회·warm·원문 검증/합성 native 추출 경합·idle을 측정했다. 측정 wrapper의
초기 parser 결과 키 오류는 실패로 보존하고 parser 구간을 고쳐 재측정했다.

실제 운영 DB의 예비 비교는 원래 백업 기준과 동일했다. writer를 멈춘 최종 비교와
tag/GHCR·digest 고정 실행체 전환·재시작/복구는 아직 수행하지 않았다. 이미지 게시와
실제 배포, 자료 지원 PARTIAL과 검사 PASS를 구분해 실행 뒤 추가한다. 모바일 실기기/PWA
설치, cold DB/OS cache와 전체 재해 복구 훈련은 미검증이다.

기존 runtime archive volume을 별도 키와 함께 read-only/network-disabled 컨테이너에서
다시 열어 모든 보관 원문의 복호화·content hash와 baseline HMAC을 확인했다. 복원본의
archive metadata는 처음 검증한 입력과 동일했다. 기존 private HTTPS mapping과 실제
HTTPS 포트/loopback gateway 및 Compose env/mount 입력도 읽기 전용으로 고정했다.

## Request-log privacy before activation

배포 입력을 검토하던 중 기본 Uvicorn 접근 로그와 Nginx 접근/요청 오류 로그가 URL의
사건 식별자·검색 매개변수를 기록할 수 있음을 확인했다. API의 `--no-access-log`와
Nginx server-level `access_log off`·`error_log /dev/null crit`를 적용했다. 이 변경은
요청 단위 프록시 오류 로그도 제거하며 기존 healthcheck·안전한 앱 경고와 DB 감사 이력은
유지한다. 컨테이너 검사에 안전하지 않은 재설정을 거부하는 회귀를 추가했다.

2026-09-09 WSL, `6aa11f0` + 해당 Dockerfile/Nginx·checker/test·문서 diff에서 실행:

- 관련 회귀 RED: 1 failed/5 passed, 누락된 세 로그 설정 때문에 실패. 수정 후 6 passed.
- 전체 Ruff format/check·mypy 356 source files와 Python **3745 passed, 822 deselected,
  3 subtests passed**, 31.82s. 앞선 Web 238/build는 UI 입력이 같아 재사용한다.
- `docker build --file infra/containers/api.Dockerfile ...`, 이어서 Web Dockerfile build 통과.
  실제 자료/키/DB/외부 AI 없이 별도 internal network와 임시 컨테이너로 실행했다.
- 동적 로그 검사에서 합성 URL의 인증 거부(401), 정상 정적 응답, 닫힌 upstream 포트의
  오류(502)를 확인했고 두 컨테이너 stdout/stderr에 합성 식별자·query marker가 없었다.
  최초 upstream 장애 fixture의 응답 조건 실패는 결과 없음으로 보존한다. 닫힌 포트로
  장애를 확실하게 만든 뒤 통과했으며 모든 소유 임시 컨테이너/network를 제거했다.
- 기존 private HTTPS의 유효 인증서·로그인 화면·비인증 거부는 Windows Chrome headless로
  확인했다. 이는 아직 새 이미지의 인증/데이터 수용 결과가 아니다.

이 후속 컨테이너 입력을 포함한 최종 PR CI와 게시 이미지는 별도로 확인한다.
