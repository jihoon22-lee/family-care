# FamilyCare v0.1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver the independently reviewable Phase 2 through Phase 8 pull requests, merge them with passing CI, and publish the Web/API/Worker containers under the `v0.1.0` tag.

**Architecture:** Preserve the React PWA, FastAPI modular monolith, PostgreSQL persistence/job queue, and Analyzer Worker. Add one vertical capability per PR, keep AI document structuring in the Worker, keep tri-state and monetary evaluation deterministic in the API, and expose only one Web gateway in the private WSL Compose runtime.

**Tech Stack:** React 19, TypeScript 6, Vite 8, Vitest 4, Python 3.14, FastAPI 0.141, Pydantic 2.13, SQLAlchemy 2.0, psycopg 3.3, PostgreSQL 18, Alembic 1.19, OpenAI Responses API, Docker Compose v2, GitHub Actions, GHCR.

**Spec:** `docs/design/v0.1-product.md`

## Global Constraints

- Branches use `<type>/<kebab-case>` with no `codex/` prefix.
- Commits use Conventional Commits and subjects no longer than 72 characters.
- Every behavior change begins with a focused test that fails for the expected missing behavior.
- PR and main CI use wholly synthetic data and never call OpenAI or Google Drive.
- Actual PDFs, extracted text, OCR images, databases, secrets, and real identifiers never enter Git, fixtures, logs, PR bodies, or CI artifacts.
- Only `AI_VERIFIED` and `USER_CONFIRMED` rules are executable.
- Only the deterministic API engine returns `MATCH`, `NO_MATCH`, `UNKNOWN`, or benefit calculations.
- Missing facts, evidence, renewal state, or unsupported rules produce `UNKNOWN`, never `NO_MATCH` or zero.
- Receipt and medical-document files are not stored; v0.1 stores manual receipt lines and claim checklist/metadata only.
- `OPENAI_API_KEY` is injected only into the Worker runtime; CI uses fake adapters.
- The default structurer model is `gpt-5.6-luna`; the default verifier model is `gpt-5.6-terra`; both IDs are non-secret runtime configuration.
- Google Drive API, Gemini, insurer submission, Cloud Run, LUKS, BitLocker, WSL swap changes, and preallocated encrypted volumes are out of scope.
- Web, Python, and Docker validation run serially; container images build one at a time after checking memory and existing containers.
- Root performs one concentrated whole-PR review immediately before each push; task-level work may use `gpt-5.6-luna` at `max` without extra review ceremonies.
- Every merged PR receives focused post-merge main verification.

No task creates a generic utility dumping ground. Each repository, service, route, schema and component has one domain owner.

## Root PR gate

Every feature plan ends with this gate plus focused tests.

- [ ] **Step 1: Confirm branch, diff, and commit range**

```bash
pwd
git status --short --branch
git diff origin/main...HEAD --stat
git log --oneline --decorate origin/main..HEAD
python3 scripts/check_git_conventions.py --range origin/main..HEAD
```

Expected: the branch matches its plan, the worktree is clean, and every commit subject passes.

- [ ] **Step 2: Run the serial repository gate**

```bash
python3 scripts/check_documentation.py
python3 scripts/check_repository_safety.py
corepack pnpm@11.22.0 web:check
TMPDIR=/tmp uv run ruff format --check .
TMPDIR=/tmp uv run ruff check .
TMPDIR=/tmp uv run mypy apps/api/src workers/analyzer/src scripts
TMPDIR=/tmp uv run pytest apps/api/tests workers/analyzer/tests scripts/tests -q
TMPDIR=/tmp uv run python scripts/check_contracts.py
TMPDIR=/tmp uv run python scripts/check_containers.py
TMPDIR=/tmp uv run python scripts/check_workflows.py
git diff --check
```

Expected: every command exits zero; no skipped or interrupted required check is reported as passing.

- [ ] **Step 3: Review the complete diff once**

Trace authorization, migration constraints, contract compatibility, failure paths, log/cache fields, generated artifacts and the feature acceptance criteria. Resolve every actionable finding before push. Do not replace this gate with repetitive per-file reviews.

- [ ] **Step 4: Push and open the PR**

```bash
branch=$(git branch --show-current)
git push --set-upstream origin "$branch"
gh pr create --base main --head "$branch" --fill
```

Expected: GitHub returns one PR URL for the exact branch.

- [ ] **Step 5: Wait for required checks and merge**

```bash
pr=$(gh pr view --json number --jq .number)
gh pr checks "$pr" --watch
gh pr merge "$pr" --merge --delete-branch
```

Expected: every required check passes and GitHub creates a merge commit. A failing check is investigated and reproduced where practical; it is never bypassed.

- [ ] **Step 6: Verify post-merge main**

```bash
git switch main
git pull --ff-only origin main
git status --short --branch
git log -1 --oneline --decorate
```

Run the feature plan's focused post-merge command and record the PR URL, merge commit, Actions run, pass counts and unverified boundaries. Do not tag or deploy outside the release plan.

## Execution protocol after the documentation PR

1. Start each plan from freshly fetched `main` on the exact branch in the ordering table.
2. Mark only the current task `in_progress` in its plan.
3. Use a fresh `gpt-5.6-luna` `max` subagent for bounded tests, fixtures, UI components or documentation when useful.
4. Root owns migrations, domain invariants, authorization, AI authority, encryption/key lifecycle, decision/calculation semantics and final integration.
5. Do not run concurrent Web, Python and Docker validation on this WSL host.
6. Do not stop processes or containers owned by other projects or Codex sessions.
7. Finish task-level commits, then perform one root whole-PR review and the shared gate.
8. Push, create the PR, wait for all required checks, merge and run focused post-merge verification.
9. Only then start the next branch.

The selected execution mode is subagent-driven in the current root session, adjusted to the user's explicit review cadence: delegation is allowed, but the formal whole-diff review occurs once at each PR gate rather than after every small task.
